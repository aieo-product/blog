## はじめに

「カバンに付けて、移動やお出かけを撮りっぱなしで記録する vlog カメラが欲しい」──そんな思いつきから、M5Stack の **Unit CamS3-5MP**（ESP32-S3 / 500万画素カメラ）を使った自作 vlog カメラを開発しました。

スマホ（PWA）から撮影状況の確認・設定・プレビュー・タイムラプス生成・SNS 投稿までできる、というのがゴールです。

```
┌─────────────────────────────────────────────┐
│ Unit CamS3-5MP / ESP32-S3                     │
│  工場OSSファーム (UnitCamS3-UserDemo) を拡張   │
│   ├─ HTTP REST API (capture / stream / 設定)  │
│   ├─ WiFi AP "UnitCamS3-WiFi" (192.168.4.1)   │
│   └─ [追加] 独自インターバラ / ファイル列挙API │
└───────────────┬───────────────────────────────┘
                │ WiFi
        ┌───────┴────────┐
        │ スマホ PWA      │  React + Vite
        │ (Cloudflare     │  ffmpeg.wasm でタイムラプス合成
        │  Pages 配信)    │  Workers 経由で X 投稿
        └─────────────────┘
```

結論から言うと、**動くものは作れました**。ただしその過程は、組み込み特有の「ドキュメントに書いていない地雷」を踏み抜く連続でした。

この記事では、開発を通じての

- 🟢 **良かったところ**（うまくいった設計判断）
- 🟡 **難しいが実現できたところ**（制約と戦って実現した機能）
- 🔴 **ハマったところ**（実機で時間を溶かした地雷集）

を、実際のコミット・パッチ・実機デバッグログをもとに振り返ります。同じボードで開発する人が同じ穴に落ちないための備忘録でもあります。

## 🟢 良かったところ

### 1. 工場 OSS ファームを「ゼロから書かず」パッチ拡張した

カメラの初期化、JPEG エンコード、WiFi AP、Web サーバ、SD ドライバ── これらをゼロから書くのは現実的ではありません。M5Stack が公開している [UnitCamS3-UserDemo](https://github.com/m5stack/UnitCamS3-UserDemo) を**フォークして拡張する**方針にしたのが、最大の正解でした。

ポイントは、工場ファームを直接書き換えるのではなく、

- **`patches/`**: 工場ファイルへの差分（`git apply` で適用）
- **`overlay/`**: 完全新規に追加するソース（独自 API など）

の2層に分けたことです。工場ファーム本体は無改変のまま `build-tree/` に置き、ビルド時にパッチを当てて overlay をコピーする。これにより「自分が何を変えたか」が常に diff として明確になりました。

### 2. パッチを番号で台帳管理した（知見がそのまま資産になる）

変更は `0001` から連番のパッチとして管理しました。

| # | 内容 |
|---|---|
| 0001 | AP 同時接続 1→4 台 |
| 0002 | カメラ既定値（黒画像対策）＋撮影時だけ高解像度へ自動切替 |
| 0003 | esp_insights の `SHA_SIZE` 未定義ビルド修正 |
| 0008 | SD マウント維持＋保存拡張子 `.jpeg`→`.jpg` |
| 0009 | メインループから撮影を駆動 |
| 0010 | FATFS の長ファイル名（LFN）有効化 |
| 0011 | **電源 ON 時に HD タイムラプス自動開始**（最終アップデート） |

各パッチのコメントに「なぜこの変更が必要か」を書き残したことで、パッチ群そのものが**地雷マップ**になりました。後述するハマりどころの多くは、このコメントに刻まれています。

### 3. 重い処理はデバイスの外へ逃がした

ESP32-S3 は本格的な動画エンコードが苦手です。そこで**タイムラプス動画の合成はデバイスでやらない**と早々に決めました。

カメラは連番 JPEG を SD に保存するだけ。動画化はスマホ PWA 内の **ffmpeg.wasm** で行い、そのまま SNS 投稿へ繋げる。X への投稿も API キーを端末に置かず **Cloudflare Workers** を中継させる。「デバイスは苦手なことをしない」という割り切りが、安定性に直結しました。

### 4. AP 同時接続を増やして実機デバッグを楽にした

工場ファームの SoftAP は `max_connection = 1`。これを 4 に上げる（パッチ 0001）だけで、**MacBook（API 叩き）と iPhone（PWA 確認）を同時にカメラへ繋げる**ようになり、デバッグ効率が一変しました。地味ですが効果は絶大でした。

## 🟡 難しいが実現できたところ

### 別タスクから SD に書けない問題を「メインループ駆動」で回避

インターバル撮影（タイムラプス）は、当初 `xTaskCreate` で専用タスクを立てて回そうとしました。ところがカメラ（DMA/PSRAM）と SD（SPI）を併用すると、**SD をマウントしたメインタスク以外からの `fopen("w")` が全て失敗**します。読み取りはできるのに書き込みだけ全 NG という不可解な挙動です。

ピン留め（`xTaskCreatePinnedToCore`）もスタック増量も mutex も効きません。タスクの「所属」が本質でした。

最終的に、専用タスクをやめて **`app_main` のメインループから毎回 `interval_tick()` を呼ぶ**方式にしました。

```cpp
extern "C" void app_main(void)
{
    APP::Setup(callback);
    while (1)
    {
        APP::Loop();
        interval_tick(); // ← 撮影・SD保存はここ（メインタスク）で駆動する
    }
}
```

「タイマで割り込む」より「ループで満了チェックする」という、組み込みらしい素朴な設計に落ち着きました。

### ライブは軽量 VGA、撮影時だけ高解像度へ動的切替

`fb_count`（フレームバッファ数）を増やすと、QSXGA（2592×1944）センサーでは DMA バッファ確保に失敗して `camera init failed` になります。つまり **`fb_count = 1` 固定**で戦うしかありません。

そこで、ライブ配信は軽量な VGA（640×480）のまま回し、静止画/タイムラプスを撮る瞬間だけ `set_framesize()` で解像度を上げ、撮り終えたら元に戻す方式にしました。解像度切替直後は旧サイズ・露出未収束のフレームが返るので、**先頭の数フレームを捨てる**のがコツです。

```cpp
s->set_framesize(s, FRAMESIZE_HD);   // 撮影解像度へ切替
for (int i = 0; i < 3; i++) {        // 切替直後の数枚は捨てる
    camera_fb_t* d = esp_camera_fb_get();
    if (d) esp_camera_fb_return(d);
}
```

### ライブと撮影のカメラ排他

`fb_count = 1` のため、ライブ配信（MJPEG ストリーム）と撮影が同時に `esp_camera_fb_get()` を呼ぶと、フレームを奪い合って Web サーバ（`async_tcp`）ごとフリーズします。そこで**タイムラプス中はライブ系 API を 503 で弾き、カメラを撮影に独占させる**ようにしました。PWA 側でも撮影中は「いま撮影」ボタンを無効化して、そもそも競合させない二段構えです。

### そして最後のアップデート：電源 ON で即 HD タイムラプス

ここまでは「スマホで開始ボタンを押す」前提でした。最後に、**カメラを電源に挿しただけで、操作ゼロで HD（1280×720）タイムラプスが始まる**ようにしました。vlog カメラとしての「撮りっぱなし」体験を、ワンタッチどころかノータッチで実現する仕上げです。詳細は後述します。

## 🔴 ハマったところ（実機デバッグ地雷集）

ここからが本題。**ドキュメントに書いていない**地雷たちです。

### 1. 撮れた画像が真っ黒

最初に撮れた写真は、完全な黒画像でした。原因は、工場ファームの初期状態で **AEC（自動露出）/ AWB（オートホワイトバランス）/ AGC（自動ゲイン）が OFF** になっていたこと。起動時にこれらを明示的に ON にするだけで解決しました（パッチ 0002）。

```cpp
sensor_t* s = esp_camera_sensor_get();
s->set_whitebal(s, 1);      // AWB
s->set_exposure_ctrl(s, 1); // AEC
s->set_gain_ctrl(s, 1);     // AGC
s->set_gainceiling(s, GAINCEILING_8X); // 暗所耐性
```

### 2. `.jpeg` だと `fopen` が errno=22（EINVAL）で失敗

SD への保存が `errno=22 (EINVAL)` で全滅。SD カードを疑い、配線を疑い、ドライバを疑い…… 真犯人は**ファイルの拡張子**でした。

FATFS の長ファイル名（LFN）が無効だと、ファイル名は **8.3 形式**（名前8文字＋拡張子3文字）に従う必要があります。`.jpeg` は拡張子が**4文字**で 8.3 非準拠。`.jpg`（3文字）に変えると、あっさり書けました。さらにサブフォルダ＋連番のパスを使うため、FATFS の **LFN を有効化**（パッチ 0010）して恒久対応しました。

> カードでもロジックでもなく、拡張子が1文字多いだけで全滅する。組み込みらしい罠でした。

### 3. SD に溜めすぎると WDT 発火 → `192.168.4.1` が接続拒否になる

テストで `/captured` 直下に画像が溜まってくると、ある日突然 `192.168.4.1` が **ERR_CONNECTION_REFUSED** で開けなくなりました。

原因は、起動時に工場コードが `/captured` を**全走査**して連番を採番する処理。ファイルが増えると SPI 読みが 5 秒を超え、**メインタスクが Watchdog（WDT）で落ちる**。Web サーバが起動する前に固まるので、接続そのものが拒否される、という芋づる式の障害でした。

対応は二段構え：

- 起動時の `/captured` 全走査を**廃止**（連番はページ側がファイル名で決めるので不要）
- 1 セッション = 1 サブフォルダ（`/captured/<日時>/`）にして、**1 フォルダあたりのファイル数を抑える**

### 4. SD 状態ポーリングが撮影中の SD をアンマウントする

`check_sdcard`（SD 情報取得）が、内部で毎回 `SD.begin()` → `SD.end()` していました。PWA が 8 秒おきに SD 状態をポーリングするので、**撮影中に SD が定期的にアンマウントされ**、保存が `fopen failed` に。マウント済みなら `begin/end` しない実装に変えて解決しました（パッチ 0008）。

### 5. `fb_count=1` のフレーム奪い合いで Web サーバが凍結

前述の通り、ライブと撮影が同時にカメラを使うと `async_tcp` が永久ブロックし、リロードすら効かない完全フリーズに陥ります。`TRY_AGAIN`（再試行）で粘ると逆効果で、コネクションが残って再びフレームを奪いに行く。**ストリーム側で `0` を返してきっぱり接続を閉じ、カメラを撮影に明け渡す**のが正解でした。

### 6. 「直したのに直らない」── USB-JTAG の自動リセットが効かない（最重要）

これで**数時間**溶かしました。

この ESP32-S3（USB-Serial/JTAG）では、`idf.py flash` の自動リセットも `esptool --after hard_reset` も `RTS/DTR パルス`も、**実機の app を再起動できません**。フラッシュは成功するのに、**古い app が RAM 上で動き続ける**のです。

結果、「コードを直して焼いたのに挙動が変わらない」→「修正が間違っている？」と疑い、無限ループに陥ります。

- **対応**: フラッシュ後は必ず **USB ケーブルを物理的に抜き差し**（電源リセット）する。
- **判定法**: 起動ログのタイムスタンプ `[123456]`(ms) が小さければ再起動成功。前回からの連続値なら未再起動＝古いファームのまま。

「焼いたら抜き差し」を儀式として徹底してから、開発速度が劇的に上がりました。

### 7. `start_poster` を叩いたら WiFi から消えてロックアウト

クラウド保存（EzData / `dest=cloud`）を試したら、設定に `startPoster=yes` が保存され、**次回起動から STA モード（既設 WiFi へ接続）に切り替わる**仕様でした。ところが WiFi の SSID が空だと接続に失敗し、**AP も立たない**。つまりカメラが WiFi 上から完全に消え、操作不能（ロックアウト）に。

- **緊急復旧**: 設定領域を消去 ── `esptool erase_region 0x410000 0x200000`
- **恒久対策**: SSID が空なら AP にフォールバックするようパッチ（0006）
- タイムラプスは STA 化しない独自インターバラ（`dest=sd`）を使う

### 8. 「読めるが書けない」SD は read-only 故障

マウント成功・容量取得 OK・ディレクトリ列挙 OK。なのに `fopen("w")` だけ全 NG。これは**SD カードの read-only 故障**でした。寿命末期の SD は書き込み保護に固着することがあります。

- **切り分け**: 無改造の工場ファームに `SD.open("/x.txt","w")` だけ足して試す。工場コードでも書けなければ実装は無罪、ハードが犯人。
- 認識・読み取りができていても、カード自体が壊れていることがある──という事実を知っているかどうかで、切り分け時間が桁違いになります。

### 9. ビルド環境の小さな罠たち

- **CMake の `GLOB_RECURSE` は configure 時評価**。新規ソースを追加しても `touch CMakeLists.txt` で再 configure しないと `undefined reference` になる。
- **esp_insights が `SHA_SIZE` 未定義**（ESP-IDF v5.1.4 互換）でビルド失敗 → `DIAG_SHA_SIZE` へ橋渡し（パッチ 0003）。
- **重いビルドは内蔵ドライブで**。外付け SSD は高負荷 I/O で切断することがある。

## 最後のアップデート：電源 ON で自動撮影

仕上げとして、**電源を入れるだけで HD タイムラプスが自動で始まる**機能を入れました。vlog カメラは「使うたびにスマホで開始ボタンを押す」のでは体験が削がれます。挿したら撮る、が理想です。

実装は、`APP::Setup()` 直後に一度だけ `interval_autostart()` を呼ぶだけ。ただし、ここにも小さな罠がありました。

- **SD は遅延マウント**：起動直後は SD が未マウントなので、`HAL::SdCardInit(true)` で明示的にマウントしてから判定する。
- **再起動で上書きしない**：RTC がなく起動時刻が取れないので、`/captured/bootNNN` の空き番号フォルダを `SD.exists()` で探して、起動ごとに別フォルダへ保存する。

```cpp
void interval_autostart()
{
    if (!HAL::IsSdCardVaild()) HAL::SdCardInit(true); // 遅延マウントを明示
    if (!HAL::IsSdCardVaild()) return;                // SDなしならスキップ

    for (int n = 1; n <= 999; n++) {                  // 空きフォルダを探す
        snprintf(g.session, sizeof(g.session), "boot%03d", n);
        char sdir[80]; snprintf(sdir, sizeof(sdir), "/captured/%s", g.session);
        if (!SD.exists(sdir)) break;                  // stat だけ＝軽量。WDTを誘発しない
    }
    g.intervalSec = 10;
    g.targetFs = FRAMESIZE_HD;  // HD 1280x720
    g.running = true;           // 実撮影はメインループの interval_tick() が行う
}
```

ここでも前述の地雷（WDT を避けるため全走査ではなく `stat` だけ使う、メインループ駆動に乗せる）が効いています。**過去のハマりが、最後の機能を素直に書ける土台になっていた**のが、地味に嬉しい瞬間でした。

## まとめ

ESP32 カメラで vlog カメラを自作して得た学びを、3 つに集約します。

- **🟢 ゼロから書かない**。OSS ファームをパッチ＋オーバーレイで拡張し、変更を番号付き台帳で管理する。差分が知見になる。
- **🟡 制約を正面から受け入れる**。`fb_count=1`、別タスクから SD 書けない、デバイスは動画エンコードが苦手── 制約を消そうとせず、制約の中で成立する設計（メインループ駆動・動的解像度切替・デバイス外合成）に倒す。
- **🔴 地雷はドキュメントに書いていない**。黒画像、拡張子1文字、WDT、USB 抜き差し── 実機でしか分からない罠は、**踏んだ瞬間に「なぜ」を残す**。それが次の自分とチームを救う。

特に **「USB-JTAG の自動リセットが効かない＝焼いても古いファームが動き続ける」** は、知らないと延々ハマる一方で、知ってさえいれば一瞬で回避できる典型でした。組み込み開発は、こういう「知っているか否か」の積み重ねだと痛感した開発でした。

同じボードで戦う誰かの、地図になれば幸いです。
